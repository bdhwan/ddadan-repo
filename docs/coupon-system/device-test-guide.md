# 실기기 검증 절차서

> 기획서 [product-spec.md §19.5](./product-spec.md#195-e2e-인수-테스트): Chrome Android·Safari iOS에서 소비자 QR, Chrome Android에서 점주 카메라 스캔을 사람이 수행한다. AI 에이전트는 실기기가 없어 이 검증을 대신할 수 없다.
> 화면 문구·버튼·경로는 2026-08-12 워크트리의 Angular 소스와 기획서 §6.2·§6.3·§7을 대조했다. 추측한 계정·URL·인증서 절차는 적지 않는다. 모르면 `미정`이다.

이 문서를 인쇄하거나 휴대폰 메모로 열어, **한 줄씩 탭**하면 된다. 결과와 증적은 아래 표의 빈칸에 적는다.

관련: [acceptance-checklist.md](./acceptance-checklist.md) · [runbook.md](./runbook.md) · [scenarios.md](./scenarios.md)

## 0. 시작 전에 막히는 것 (확정 전)

아래가 채워지기 전에는 표의 여러 항목이 로그인·카메라 단계에서 멈춘다. **지어내지 말고 출력을 그대로 옮긴다.**

| 항목 | 상태 | 무엇을 알아야 하는가 |
|---|---|---|
| 테스트 계정·ACTIVE 상점·활성 도장 정책 | **미정 — 시드 도구 출력 참조** | 시드 도구가 만드는 소비자/점주 이메일·비밀번호, ACTIVE 상점, 활성 도장 정책. 도구 경로·사용법은 [runbook.md](./runbook.md) 「시드 도구」 |
| 앱 로그인 | **미정** | 소비자·점주 로그인 화면(`libs/coupon-ui/.../auth-route.component.ts`)은 제출을 `preventDefault` 하고 Firebase `signInWithEmailAndPassword` 호출이 없다. `environment.ts` Firebase 값은 placeholder. 시드 계정으로 실기기 로그인하는 방법(연동 완료 여부 포함)은 인증/시드 작업이 끝난 뒤 이 칸을 갱신한다 |
| HTTPS 주소·자체 서명 인증서 경고 | **미정** | 점주 카메라는 `window.isSecureContext` 가 아니면 「HTTPS 연결이 필요함」을 보여 준다(`store-scan.component.ts`). iOS Safari / Android Chrome 의 인증서 경고 통과 절차는 HTTPS 서빙을 구성하는 쪽의 보고를 이 절에 붙인다 |
| LAN Origin allowlist | **미정** | `.env.coupon.example` 의 `COUPON_ALLOWED_ORIGINS` 는 `http://localhost:4310,4320,4330` 만 있다. 휴대폰이 `https://192.168.150.185:…` 로 열면 Origin 이 달라 상태 변경 API 가 거절될 수 있다. 확정 HTTPS origin 을 받은 뒤 개발 머신 `.env.coupon` 에 추가했는지 적는다 |

HTTP LAN 으로도 **소비자 QR 표시·오프라인 안내**(D-01, D-02, D-05, D-07, D-08, D-09 소비자)는 시도할 수 있다. 점주 `getUserMedia` 카메라(D-03)는 HTTPS 없이는 실패하는 것이 정상이다. 그때는 D-04 수동 코드로 우회한다.

## 1. 사전 준비

### 1.1 네트워크

- 개발 머신 LAN IP: **`192.168.150.185`** (`rtx-5090-ubuntu`).
- 휴대폰을 **같은 Wi-Fi**(사무실/매장 전용 공유기, 동일 SSID)에 연결한다.
- 휴대폰 브라우저에서 `http://192.168.150.185:7810/api/coupon/v1/health/live` 가 응답하는지 먼저 본다. API 는 `COUPON_BIND_ADDR=0.0.0.0:7810` 이라 LAN 에서 닿는다.

### 1.2 서버·앱 기동 순서

근거: [README.md](./README.md) 「로컬 개발 시작 순서」, `scripts/coupon/db-up.sh`, `package.json` 의 `dev:coupon-*`.

개발 머신(저장소 루트)에서 **이 순서대로** 한다. 실기기 검증은 개발 DB(`coupon`)를 쓴다. 테스트 DB(`coupon_test`)로 바꾸지 않는다.

1. Postgres / Redis
   ```bash
   ./scripts/coupon/db-up.sh
   ```
2. 환경변수. 저장소 루트 `.env.coupon.example` 을 복사해 `.env.coupon` 을 만든다(비밀은 커밋하지 않음).
   ```bash
   set -a && . ./.env.coupon && set +a
   ```
3. 마이그레이션. `sqlx-cli` 는 `COUPON_` 접두사를 모르고, 역할명 `coupon` 과 스키마가 겹치면 추적 테이블이 샌다(`scripts/coupon/db-test-up.sh` 주석).
   ```bash
   cd apps/coupon-api-server
   PGOPTIONS='-c search_path=public' sqlx migrate run
   cd ../..
   ```
4. API
   ```bash
   cargo run --bin coupon-api
   ```
   확인: `curl -s http://127.0.0.1:7810/api/coupon/v1/health/ready`
5. Angular 앱을 **LAN 에 바인딩**해서 띄운다. `package.json` 의 `start` 는 `ng serve --port …` 뿐이라 기본은 localhost 전용이다. 휴대폰이 붙으려면 `--host 0.0.0.0` 이 필요하다.
   ```bash
   npm run start --workspace coupon-consumer-app -- --host 0.0.0.0
   npm run start --workspace coupon-store-app -- --host 0.0.0.0
   # 관리자 화면이 필요할 때만
   npm run start --workspace coupon-system-admin-app -- --host 0.0.0.0
   ```
6. 시드 도구로 ACTIVE fixture 를 넣는다 → **미정 — 시드 도구 출력 참조** ([runbook.md](./runbook.md) 「시드 도구」).
7. Firebase Auth emulator: 다른 에이전트가 `apps/coupon-api-server/scripts/auth-emulator.sh` 를 추가 중이다(이 문서 작성 시점 미커밋). 스크립트 헤더는 `up` 시 `0.0.0.0:9099`, LAN `192.168.150.185:9099` 를 말한다. **서버 `config.rs` / `.env.example` 에는 `COUPON_FIREBASE_AUTH_EMULATOR_HOST` 가 아직 없고**, Angular `connectAuthEmulator` 호출도 없다. 로그인 연동이 끝나기 전에는 이 단계를 필수로 두지 않는다.

`coupon-worker` 는 이 절차서의 QR·스캔·적립 동기 경로에 필수가 아니다.

HTTPS 기동 명령(포트, 인증서 경로, `ng serve --ssl` 여부): **미정**. 확정되면 이 목록 5번 옆에 붙이고 §1.5 를 채운다.

### 1.3 접속 URL

`ng serve` + `proxy.conf.json` 이 `/api/coupon/v1` 을 `http://localhost:7810` 으로 넘긴다. 휴대폰은 앱 포트만 연다.

| 역할 | 앱 | HTTP (현재 확정) | HTTPS |
|---|---|---|---|
| 소비자 | `coupon-consumer-app` | `http://192.168.150.185:4310` | **미정** |
| 점주 | `coupon-store-app` | `http://192.168.150.185:4320` | **미정** (카메라에 필요) |
| 운영 관리자 | `coupon-system-admin-app` | `http://192.168.150.185:4330` | **미정** |
| API 직접 | `coupon-api` | `http://192.168.150.185:7810/api/coupon/v1` | **미정** |

로그인 화면 경로: 소비자·점주 모두 `/login`. 내 QR: `/my-qr`. 점주 스캔: `/scan`.

### 1.4 테스트 계정

시드 도구가 아직 저장소에 없다(`scripts/coupon/` 에는 DB 기동·테스트 스크립트만 있음). **추측한 이메일/비밀번호를 적지 않는다.** 도구를 실행한 뒤 출력 그대로 옮겨 적는다.

| 역할 | 이메일 | 비밀번호 | 기대 상태 | 비고 |
|---|---|---|---|---|
| 소비자 A | 미정 — 시드 도구 출력 참조 | 미정 | 활성 회원, 필수 약관 동의, QR 발급 가능 | D-01, D-02, D-05, D-07, D-08 |
| 소비자 B (두 번째 기기) | 미정 — 시드 도구 출력 참조 | 미정 | 소비자 A 와 **같은 계정**이거나, 도구가 지정한 다중 기기 계정 | D-07. 같은 회원이면 됨 ([WALLET-004](./scenarios.md#wallet-004-여러-기기타)) |
| 점주 | 미정 — 시드 도구 출력 참조 | 미정 | `STORE_OWNER`, 상점 `ACTIVE`, 도장 정책 `ACTIVE` | D-03, D-04, D-06, D-09, D-10 |
| 관리자 | 미정 — 시드 도구 출력 참조 | 미정 | 이 절차서 10항목에는 필수 아님 | 관리자 로그인도 `preventDefault` shell |

ACTIVE fixture (시드 출력에서 옮겨 적기):

| 항목 | 값 |
|---|---|
| 상점 slug / 표시명 | 미정 — 시드 도구 출력 참조 |
| 상점 상태 | `ACTIVE` 이어야 한다 |
| 활성 도장 정책 | 있어야 한다. 목표 수 기본 10 ([product-spec §8.1](./product-spec.md#81-도장-정책)) |
| 소비자–상점 관계 | 관심 등록 또는 적립 이력. 시드가 만들지 않으면 첫 스캔에서 생성되는지 시드 README 를 본다 |

### 1.5 자체 서명 인증서 경고 통과

점주 스캔은 HTTPS secure context 에서 `getUserMedia` + `facingMode: { ideal: "environment" }` 를 쓴다 ([product-spec §7](./product-spec.md#7-반응형pwa접근성-요구사항)).

| 브라우저 | 절차 |
|---|---|
| Android Chrome | **미정** — HTTPS 서빙 구성 쪽의 확인 결과를 이 칸에 붙인다. 아직 없으면 HTTP LAN 에서 「HTTPS 연결이 필요함」이 뜨는 것이 현재 구현이다 |
| iOS Safari | **미정** — Android 와 다르다. 프로파일 설치·인증서 신뢰·예외 허용 중 무엇이 필요한지 확인 전까지 적지 않는다 |

## 2. 검증 항목 추적표

빈칸(`실제 결과`, `증적`)은 수행자가 채운다. 증적 파일명은 `YYYYMMDD-HHmm-D0n-<기기>-<내용>.png` 형식(예: `20260812-1430-D01-pixel-qr.png`). 스크린샷은 이 문서와 같은 디렉터리의 `device-test-evidence/` 에 두거나, 파일명을 표에만 적어도 된다.

## 3. 탭 단위 상세 (표만으로 부족할 때)

### D-01 Android Chrome — 소비자 QR

1. Chrome으로 `http://192.168.150.185:4310/login` (또는 §1.3 HTTPS)을 연다.
2. 「이메일」「비밀번호」를 채우고 **`로그인`** 을 탭한다. (연동이 안 되어 반응이 없으면 §0을 기록하고 중단. 추측 계정으로 우회하지 않는다.)
3. 하단 내비에서 **`내 QR`** 을 탭한다. (`/my-qr`)
4. 보이는지 체크한다.
   - 제목 영역 「내 QR」, eyebrow 「60초 회전형」
   - 「결제 QR이 아닙니다」
   - 정사각 QR, 「남은 시간」+초
   - 「카메라가 안 될 때 8자리 보조 코드」와 숫자
   - 「화면 캡처 공유 시 다른 사람이 먼저 사용할 수 있습니다.」
5. 초가 1초씩 줄어드는지 10초간 본다.
6. 30초 전후 「새 QR 갱신 중」→ 보조 코드가 바뀌는지 본다. (기획서 WALLET-003: 유효 60초, 화면은 30초마다 교체.)
7. 증적: QR이 보이는 화면, 갱신 직후 코드가 바뀐 화면.

### D-02 iOS Safari — 배경 복귀

1. Safari로 소비자 URL `/login` → 로그인 → **`내 QR`**.
2. 타이머가 돌아가는 화면을 찍는다.
3. 홈으로 나갔다가, 가능하면 **70초 이상** 기다린다(만료 경로). 짧게 나갔다 와도 「복귀 후 갱신/만료 UI」는 관찰 대상이다.
4. 앱 전환기로 Safari를 다시 연다.
5. 만료면 「QR 유효시간이 끝났어요」/「만료된 QR은 사용할 수 없습니다…」/ **`QR 다시 만들기`**. 탭 후 새 QR.
6. 증적: 복귀 직후 화면.

### D-03 Android Chrome — 점주 카메라

1. Chrome으로 점주 HTTPS URL `/login` → 점주 계정.
2. 상단/측면 내비 **`스캔`** (`/scan`). 페이지 제목 「고객 QR 스캔」.
3. 첫 진입에서 시스템 카메라 권한 다이얼로그 → **허용**.
4. HTTP 이면 「HTTPS 연결이 필요함」/「안전한 HTTPS 주소에서 다시 열거나 보조 코드를 입력하세요.」→ D-03 은 실패로 적고 HTTPS URL 을 기다린다. 수동 입력은 D-04.
5. 미리보기가 매장 쪽(후면)을 비추는지 확인한다. 셀카(전면)만 나오면 실패.
6. 소비자 QR을 파인더 네모에 맞춘다. 「QR을 확인하고 있습니다. 중복 프레임은 처리하지 않습니다.」가 잠깐 보일 수 있다.
7. 「고객을 안전하게 확인했습니다」+ 마스킹 이름 + 가용 도장 수.
8. 증적: 권한 직후 미리보기, resolve 성공.

### D-04 권한 거부 + 8자리

1. 점주 Chrome 사이트 설정에서 카메라 **차단** 후 `/scan` 을 새로고침한다. (이미 허용한 사이트면 자물쇠 → 권한 → 카메라 차단.)
2. 「카메라 권한이 거부됨」.
3. 오른쪽/아래 「카메라를 사용할 수 없나요?」카드에서 8자리만 입력. **이메일·전화 칸이 있으면 실패**(STORE-005).
4. 소비자 화면 코드를 공백 없이 넣는다. **`보조 코드 확인`**.
5. D-03과 같은 resolve 화면이면 통과.

### D-05 오프라인

1. **`내 QR`** ready 상태에서 비행기 모드.
2. 아이콘 `⌁`, 제목 「인터넷 연결이 필요해요」, 버튼 **`연결 후 다시 확인`**. QR 격자·큰 8자리가 남아 있으면 실패.
3. 비행기 모드 해제 후 버튼 탭 → 다시 QR.

### D-06 응답 유실과 멱등키

적립(도장) 경로로 수행한다. 쿠폰 사용도 같은 FAILURE UI(`uncertain` + **`처리 결과 확인`**)를 쓰지만, 사용은 예약·쿠폰 ID가 더 필요하므로 이 절차서는 도장을 기본으로 한다.

1. 점주 기기로 고객을 resolve 하고 **`거래 입력 계속`**.
2. 「도장 적립」이 선택된 것을 확인. 「주문 금액」에 `1000` (원). 품목은 비워도 된다(최소 금액 0 기본).
3. **`승인 전 검토`** → 마스킹 고객·예상 적립이 보이면 **`도장 적립 승인`**.
4. 「도장을 반영하고 있습니다」/「창을 닫거나 승인 버튼을 다시 누르지 마세요.」가 보이면 **점주 기기만** 네트워크를 끊는다. 소비자 QR 폰은 켜 둬도 된다.
5. FAILURE 에서 「요청 식별」코드(멱등키)를 적는다.
6. 네트워크 복구 → **`처리 결과 확인`**. 성공이면 거래 ID 1개. 같은 주문을 **`다음 고객`** 없이 한 번 더 승인하는 버튼을 누르지 않는다.

서버에 두 번 적립됐는지는 시드/관리자 거래 탐색 또는 API `GET` 이 있으면 그 증적을 붙인다. 관리자 로그인·시드가 미정이면 점주 성공 화면의 거래 ID 가 확인 전후 동일한지만 적고, 원장 이중 기록은 **미검증**으로 남긴다.

### D-07 다중 기기 QR

1. 같은 소비자로 기기 A·B 에서 **`내 QR`**.
2. 코드 A / 코드 B / 남은 시간을 표에 적는다. 같으면 실패(동시에 발급했는데 동일 nonce).
3. 점주는 A 만 사용(스캔 또는 수동).
4. B 화면이 즉시 빈 화면·「이미 사용」이 되면 실패. B 는 살아 있어야 한다(WALLET-004).

### D-08 wake lock

1. **`내 QR`** 하단 문구를 그대로 적는다.
2. **`지갑`** 으로 나갔다가 화면이 다시 어두운 테마/이전 배경인지 본다. (구현은 `documentElement` background·colorScheme 를 들어올 때 저장하고 나갈 때 복구, wake lock release.)
3. iOS Safari 는 Wake Lock 미지원인 경우가 많다. ◐ 문구면 「해당 없음(미지원)」으로 통과 처리하고, 떠나도 브라우저가 멈추지 않는지만 본다.

### D-09 360px

1. 데스크톱 Chrome F12 → 기기 모드 360×800.
2. 소비자 `/`, `/wallet`, `/my-qr` 에서 가로 스크롤 바가 본문에 생기는지.
3. 점주 `/scan` READY·INPUT.
4. 실기기에서도 같은 화면을 가로로 밀어 본다.

### D-10 성공/실패 구분

성공 화면 필수 요소: `✓` · 제목 · 본문 설명 · `거래 ID` `<code>` · 처리 시각 · **`다음 고객`**.

실패/불확실 화면 필수 요소: `×` · 제목 · 본문 · 거래 ID 또는 「아직 확인되지 않음」 · 요청 식별.

색(초록/빨강)만 다르고 제목·ID 가 없으면 실패.

## 4. 실패 시 대응

근거: [product-spec.md §18.3](./product-spec.md#183-로그trace). 모든 API 응답 JSON 에 `request_id` 가 있다(`apps/coupon-api-server/README.md`, 테스트 `every_response_carries_a_request_id`).

통과하지 못한 항목마다 다음에 적는다. **색만 보고 “안 됨”이라고 쓰지 않는다.**

| 기록 | 어디에 |
|---|---|
| 항목 번호 (D-0n), 기대 vs 실제 | 위 추적표 `실제 결과` |
| 재현 절차 (탭 순서, 비행기 모드 시각) | 표 + 이 절 메모 |
| 기기 모델, OS, 브라우저 버전, 접속 URL | §1.6 과 동일하게 |
| 시각 (KST) | 증적 파일명과 표 |
| 화면의 거래 ID, 요청 식별(멱등키), 에러 코드/문구 | 표 `증적` |
| `request_id` | 네트워크 패널 또는 에러 JSON `error.request_id` / 성공 `request_id`. 앱이 화면에 안 보여 주면 그 사실을 적는다 |
| 스크린샷 | `device-test-evidence/` |

보고 위치: **미정** (운영 온콜 채널·티켓 보드가 [runbook.md](./runbook.md) 에도 미정). 출시검증 코디네이터에게 이 문서의 채워진 표와 증적 경로를 넘긴다. 로그 조회는 API 구조화 로그의 `request_id` · 인증 후 `actor_id` · 상점 `store_id` · 변경 `transaction_id` 로 한다(§18.3).

같은 항목을 재시도할 때 시드를 다시 돌릴지는 시드 도구 문서(**미정**)를 따른다. 한도·nonce 소비로 재현이 안 되면 새 소비자 QR 을 발급하고 표에 「재시도 n」을 적는다.
